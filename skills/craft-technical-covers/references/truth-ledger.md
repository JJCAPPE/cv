# Truth ledger

Build the ledger before drawing. It is the boundary between documented system visualization and invented technical decoration.

## Source hierarchy

Use the highest available authority for each claim:

1. Current executable code, model definitions, schemas, and checked-in configuration.
2. Tests and reproducible runtime artifacts generated by that code.
3. Versioned datasets, model cards, evaluation outputs, and deployment manifests.
4. Current architecture documents that agree with implementation.
5. Historical reports, concept diagrams, presentations, and mockups.
6. Visual references used only for art direction.

Do not let a polished historical flowchart override current code. Do not infer runtime behavior from filenames or imports alone; follow the active entry point and configuration.

## Required ledger fields

Record one entry for every visible claim:

| Field | Meaning |
| --- | --- |
| `id` | Stable short identifier used by the generator or review notes |
| `display` | Exact label or number shown in the artwork |
| `claim` | What the visual asserts |
| `source` | Repository path plus symbol, section, key, or artifact |
| `scope` | `default`, `optional`, `offline`, `historical`, or `proposed` |
| `surfaces` | `master`, `cover`, `companion`, or `caption` |
| `confidence` | `verified`, `qualified`, or `excluded` |
| `notes` | Ambiguity, units, provenance, or display constraint |

Start from `assets/technical-cover-starter/truth-ledger.template.json` when useful. Keep exclusions in the same ledger so stale concepts do not return during polishing.

## Software truth rules

- Trace the actual entry point through its call and data boundaries.
- Separate supervisory control from lower-level workers, schedulers, queues, callbacks, or hardware timing.
- Show concurrency only when it exists in the current implementation. Name the boundary precisely.
- Show state transitions only when the transition is implemented and reachable.
- Distinguish persisted state, in-memory state, telemetry, and visualization.
- Show external services only when configured or invoked by the current path.
- Do not turn utility modules into runtime stages merely because they exist.
- Represent optional flags, feature gates, fallbacks, and experimental paths as dashed branches with explicit labels.

## ML truth rules

Audit training and inference separately. They often share components but are not the same runtime.

### Data

- Identify the actual dataset version, split strategy, filters, labels, and transformations.
- Do not imply live streaming when the pipeline is batch, or a feature store when features are local files.
- Do not draw raw data examples that disclose sensitive or private content.

### Model

- Derive model family, inputs, outputs, and major components from current definitions or a versioned model artifact.
- Do not infer parameter count, context length, embedding dimensions, or topology from a project description.
- Label third-party foundation models and hosted APIs accurately; do not depict them as locally trained models.

### Training and evaluation

- Separate training-only stages from serving.
- Show hyperparameter search, distributed training, or accelerators only when configured and used.
- Display metrics only from a reproducible, identified artifact. Include split and unit when needed.
- Never use illustrative numbers in a technical cover.

### Inference and serving

- Trace preprocessing, request shaping, model invocation, postprocessing, storage, and response paths.
- Distinguish synchronous calls, queues, batch jobs, caches, and human review.
- Mark observability as evidence or feedback, not as training data, unless the feedback loop is implemented.

## Qualification patterns

When exact structure is unknown but a concept is real:

- use a labeled schematic volume rather than fabricated internal geometry;
- use `DOCUMENTED INTERFACE` rather than a guessed protocol;
- move precise caveats into the caption;
- omit hidden relationships;
- label proposed work as `PROPOSED`, never as a default path.

## Final audit

Before integration, read the image label by label and arrow by arrow. For each one, point to a ledger entry and its source. Remove anything that cannot pass this audit.
