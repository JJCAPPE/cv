## 3. Claims removed or downgraded during validation

The following corrections materially changed the initial research direction.

### Removed: “generic state-aware agent reliability lab” as the selected project

**Reason:** ConsequenceBench, Open-Weight Agent Reliability Lab, AgentProbe, and AgentReplay already cover large parts of deterministic faults, state correctness, authorization, retries, idempotency, readback, replay, and CI regression.

**Correction:** the selected contribution is multi-tenant configuration-matrix release impact plus measured component attribution. State/fault/replay mechanisms remain implementation components, not the novelty claim.

### Removed: unverified warm Kulis-to-Sami/Maven path

**Reason:** connected sources verify Giacomo's direct relationship with Brian Kulis but do not verify that Brian knows Sami Shalabi or another Maven employee.

**Correction:** A strength applies only to Giacomo→Brian. The path beyond Brian is unusable until Brian independently confirms a contact.

### Removed: Banca Mediolanum or Databricks employee introduction path

**Reason:** no connected email/contact evidence established a first-degree employee who can introduce Giacomo to Maven.

**Correction:** these backgrounds remain candidate-fit evidence, not connection evidence.

### Removed: GitHub follower/contributor mutual path

**Reason:** connected GitHub searches found no relevant mutual contribution, issue, pull request, or organization path.

**Correction:** Maven GitHub is used as technical product evidence only.

### Downgraded: schema drift, idempotency, partial action failure, and rare-failure replay as “internal Maven problems”

**Reason:** public product/hiring evidence makes these credible engineering risk classes, but Maven has not publicly disclosed them as incidents or deficiencies.

**Correction:** they are labeled strong inference or confirmed problem space, never confirmed Maven failure.

### Downgraded: release gate across every customer configuration

**Reason:** Maven publicly confirms simulations/regression testing and customer-specific FDE validation, but not the exact matrix-wide attribution system proposed here.

**Correction:** “customer-specific release gates and attribution” is a strong inference/open project question, not a statement about missing internal tooling.

### Removed: unsupported company-performance rationale

**Reason:** exact revenue, customer count, valuation, or deployment totals are not necessary to choose the technical artifact and may be self-reported or time-sensitive.

**Correction:** the recommendation rests on product/hiring/technical fit. A field-report deployment count is noted only as self-reported context in the source registry.

## 6. Project-novelty validation

TenantDiff remains nonredundant only while all six conditions hold:

1. the experimental unit is a tenant/role/channel configuration, not a generic agent run;
2. releases are decomposed into immutable, swappable component manifests;
3. intended changes are declared before evaluation;
4. blast radius is measured across the matrix;
5. counterfactual substitutions produce attribution metrics against known injected causes;
6. results are compared with output-, trajectory-, state-, and replay-only baselines.

A project that drops these conditions should not use the TenantDiff novelty claim.
